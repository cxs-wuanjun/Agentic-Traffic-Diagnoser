# 交通诊断报告生成工作流 Skill

当用户请求“交通诊断报告、综合分析、分析报告、事件报告”时，使用本 Skill 约束完整报告生成链路，而不是只约束最终排版。

## 工作流

1. Draft：根据工具返回的真实交通数据生成报告初稿。
2. Review：审查初稿中的数据引用、成因分析、处置建议和格式完整性。
3. Refine：根据审查意见修订报告，删除无依据结论，补充必要的数据来源说明。
4. Assemble：在最终报告之后生成可执行 Python 代码，用于图表生成和 Word 装配。

## Draft 阶段要求

- 必须先识别分析对象、报告类型和可用数据来源。
- 所有定量描述必须来自工具结果或明确标注数据不足。
- 成因分析只能基于已查询到的数据、道路状态、事件记录或知识库依据。
- 处置建议必须在初稿中出现，不能等到最终装配阶段才补充。
- 若能够判断异常类型，需将其归为拥堵、事故、施工或其他交通异常；无法判断时必须说明依据不足。

## Review 阶段要求

审查者需要逐项检查：

- 数据引用是否能追溯到工具返回内容。
- 是否存在凭空推断、扩大结论或伪造指标。
- 成因分析是否与交通状态、事件记录或知识库依据一致。
- 处置建议是否具体、可执行，并与异常类型匹配。
- 报告结构是否完整，是否存在标题缺失、格式漂移或重复段落。

若报告满足要求，可以返回 PASS；否则给出具体修改意见。

## Refine 阶段要求

- 根据 Review 意见修订完整报告。
- 保留有依据的分析，删除无依据的结论。
- 对数据不足的部分，用“当前数据不足以支撑该判断”明确标注。
- 处置建议应结合内置 SOP 预案库和当前异常类型，避免空泛表述。
- 最终输出应先给出完整 Markdown 报告，再在末尾提供 Python 代码块。

## Assemble 阶段要求

- 如果历史数据足以支撑趋势图，按 data-visualization Skill 生成图表。
- 按 docx-assembler Skill 将报告正文、图表和附加说明装配为 Word。
- 若报告中识别出拥堵、事故或施工类型，按 compliance-sop Skill 读取对应 SOP 内容，并写入报告正文或 Word 附录。
- Python 代码必须保存最终 Word 到 `outputs/reports/Final_Report.docx`。

## 边界约束

- 不得伪造数据来源、指标数值、事故记录或官方结论。
- 不得把内置 SOP 预案库表述为真实外部官方文件，除非数据源明确支持。
- 不得只输出排版代码而忽略报告正文质量。
